# Preliminary Phase

**Purpose:** Prepare the **organization** to do enterprise architecture — not the vision for a single initiative.

## Key terms

| Term | Short description |
|------|-------------------|
| **Scope** | Boundaries of EA work in the organization: what EA covers and what sits outside it for this context. |
| **Principles** | Architecture **decision rules** that constrain choices so trade-offs are resolved **consistently** with strategy. TOGAF template: **Name**, **Statement**, **Rationale**, **Implications**. |
| **Frameworks** | Tailored **ADM** plus methods, templates, and structures so EA work is **repeatable**, not ad hoc. |
| **EA capability** | **People, roles, skills, and processes** needed to **run** EA (the function), not the architecture diagrams themselves. |
| **Governance basics** | **Who decides**, how **escalation** and **compliance** work for architecture so ADM outputs can be enforced. |

## Functions (exam level)

- Establish or improve **enterprise architecture capability** and **governance**.
- Agree **architecture principles** (Name / Statement / Rationale / Implications) and **tailoring** of the method to the enterprise.
- Align the **scope** of EA with organizational context and strategy.

## Architecture Principle template (exam)

| Part | Meaning |
|------|---------|
| **Name** | Memorable essence of the rule; avoid specific technology platforms. |
| **Statement** | Clear, unambiguous fundamental rule. |
| **Rationale** | Business benefits of adhering to the principle. |
| **Implications** | Business/IT requirements, costs, activities; impact if not followed. |

## Links to other phases

- **Enables all later phases:** Without capability and governance, cycles lack authority and consistency.
- **Requirements Management:** When ADM cycles run, requirements work still flows through the central hub.

## Key deliverables (create / update)

| Deliverable | In Preliminary |
|-------------|----------------|
| **Architecture Principles** | **Established** (Name / Statement / Rationale / Implications) |
| **Organizational Model for EA / tailored framework** | **Established** |
| **Architecture Repository** (structure/use) | Often **initialized** |
| **ADD / Roadmap** | **Not** produced here |

## Industry note: “Architecture Charter” (not a classic TOGAF exam name)

In practice, an **Architecture Charter** (EA “constitution”: mandate, scope, authority, governance, roles, sponsorship) aligns with **Preliminary** intent — especially the **Organizational Model for EA**, **governance/decision rights**, and **principles**.

| Don’t confuse | With |
|---------------|------|
| **EA charter / Organizational Model (Preliminary)** | Standing mandate for the **EA function** |
| **Statement of Architecture Work (Phase A)** | Approval to run **this** architecture cycle / initiative |

For OGEA-101, prefer TOGAF wording (**Organizational Model**, principles, tailored framework, governance). Treat “Architecture Charter” as a useful practice label for the same Preliminary ideas — not a separate deliverable to memorize.

## Boundaries

- **Not Phase A:** Preliminary does **not** produce the **Architecture Vision** or initiative-specific **business case** / **Statement of Architecture Work** — that is Phase A.
- **Not B/C/D:** Does **not** develop domain architectures (business, IS, technology) in detail.
